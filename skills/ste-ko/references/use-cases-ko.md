# 유형별 패턴

## 채팅 답변

- 첫 문장에 결론을 쓴다.
- 근거는 결론 뒤에 짧게 쓴다.
- 확인한 것과 확인하지 못한 것을 나눈다. 실행하지 않은 검사는 통과했다고 쓰지 않는다.
- 사용자가 결정해야 하면 번호 선택지를 쓴다. 추천을 첫 번째에 두고 "(권장)"을 붙인다.

## 오류 메시지

1. 무엇이 실패했는지 쓴다.
2. 원인을 안다면 원인을 쓴다. 모르면 쓰지 않는다.
3. 사용자가 할 일을 명령형 한 문장으로 쓴다.

예: "설정 파일을 읽지 못했습니다. 경로를 확인하세요. 현재 경로는 `C:\app\config.toml`입니다."

## 런북과 절차서

- 번호 목록을 쓴다. 한 단계에 동작을 하나만 쓴다.
- 조건을 동작 앞에 쓴다.
- 동작의 결과는 다음 문장에 쓴다.
- 되돌릴 수 없는 단계 앞에 경고를 쓴다. 경고의 첫 문장은 해야 할 일이나 하지 말아야 할 일이다.

## 사고 보고서

- 첫 문장에 영향과 현재 상태를 쓴다.
- 시간 순서는 번호 목록이나 표로 쓴다.
- 원인을 모르면 "원인을 확인하지 못함"이라고 쓰고 확인 방법을 쓴다.
- 재발 방지는 실행할 수 있는 동작으로 쓴다.

## 릴리스 노트와 변경 이력

- 사용자에게 보이는 변화를 먼저 쓴다.
- 한 항목에 변화를 하나만 쓴다.
- 영문 커밋 메시지는 이 스킬의 대상이 아니다. 프로젝트의 커밋 규칙을 따른다.

## UI 문구

- 버튼은 동사로 쓴다. 예: "저장", "삭제".
- 오류 문구는 오류 메시지 패턴을 따른다.
- 같은 동작에는 같은 단어를 쓴다.

## 에이전트에게 주는 지시문

- 목적, 범위, 완료 조건을 각각 한 문장으로 쓴다.
- 하지 말아야 할 일을 명시한다.
- 같은 대상에는 지시문 전체에서 같은 이름을 쓴다.
- 파일 경로와 명령은 원문 그대로 쓴다.

## 번역 준비

- 한 문장에 한 사실만 쓴다.
- 주어를 생략하지 않는다.
- 관용구와 비유를 쓰지 않는다.
