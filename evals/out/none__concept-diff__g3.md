## 핵심 차이

둘 다 한 브랜치의 변경 사항을 다른 브랜치에 합치는 명령이지만, **히스토리를 다루는 방식**이 다릅니다.

### git merge
두 브랜치를 합치는 **머지 커밋**을 새로 만들어 히스토리를 보존합니다.

```
      A---B---C  feature
     /         \
D---E---F---G---M  main
```

- 기존 커밋은 그대로 유지됨 (해시 변경 없음)
- 히스토리가 분기·합류 형태로 남음 (실제 작업 흐름 그대로)
- 안전하고 되돌리기 쉬움

### git rebase
feature 브랜치의 커밋들을 main의 최신 커밋 **뒤로 옮겨 다시 적용**합니다.

```
D---E---F---G---A'---B'---C'
```

- 커밋이 새로 만들어지므로 **커밋 해시가 바뀜**
- 히스토리가 일직선으로 깔끔해짐
- 머지 커밋이 생기지 않음

## 비교

| | merge | rebase |
|---|---|---|
| 히스토리 | 분기 구조 유지 | 선형으로 정리 |
| 기존 커밋 | 변경 없음 | 새 커밋으로 재작성 |
| 머지 커밋 | 생성됨 | 생성 안 됨 |
| 충돌 해결 | 한 번에 | 커밋별로 여러 번 가능 |
| 위험도 | 낮음 | 공유 브랜치에선 높음 |

## 사용 가이드

- **rebase**: 내 로컬 feature 브랜치를 최신 main 기반으로 갱신하거나, PR 전에 커밋을 정리할 때 (`git rebase -i`)
- **merge**: feature를 main에 최종 통합할 때, 또는 여러 사람이 함께 쓰는 공유 브랜치

## 주의: 황금률

> **이미 push해서 다른 사람이 쓰고 있는 브랜치는 rebase하지 마세요.**

해시가 바뀌어 다른 사람의 히스토리와 어긋나고, force push가 필요해져 협업에 문제가 생깁니다.

## 기본 사용법

```bash
# merge
git checkout main
git merge feature

# rebase
git checkout feature
git rebase main
```
