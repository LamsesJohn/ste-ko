## 핵심 차이

둘 다 한 브랜치의 변경 사항을 다른 브랜치에 합치는 명령이지만, **히스토리를 다루는 방식**이 다릅니다.

### git merge
두 브랜치의 끝을 합치는 **머지 커밋**을 새로 만듭니다. 기존 커밋은 그대로 보존됩니다.

```
      A---B---C  feature
     /         \
D---E---F---G---M  main
```

- 히스토리가 실제로 일어난 그대로 남음 (분기와 병합 기록 유지)
- 기존 커밋을 건드리지 않아 안전함
- 머지가 잦으면 히스토리가 복잡해짐

### git rebase
feature 브랜치의 커밋들을 main의 최신 커밋 **뒤에 다시 쌓아서** 재작성합니다. 커밋 해시가 새로 만들어집니다.

```
            A'--B'--C'  feature
           /
D---E---F---G  main
```

- 히스토리가 일직선이라 깔끔함
- 머지 커밋이 없음
- 커밋이 복제·재작성되므로 **이미 push한 공유 브랜치에는 위험**함

## 비교표

| | merge | rebase |
|---|---|---|
| 히스토리 | 분기/병합 그대로 보존 | 선형으로 재작성 |
| 머지 커밋 | 생김 | 없음 |
| 커밋 해시 | 유지 | 변경됨 |
| 충돌 해결 | 한 번에 | 커밋마다 나올 수 있음 |
| 공유 브랜치 | 안전 | 위험 (force push 필요) |

## 실무 가이드

- **rebase**: 내 로컬 feature 브랜치를 최신 main 위로 정리할 때 (`git rebase main`)
- **merge**: feature를 main에 합칠 때, 또는 여러 사람이 쓰는 브랜치일 때
- **황금률**: 다른 사람과 공유한 브랜치(이미 push된 커밋)는 rebase하지 않기

흔한 워크플로우는 "작업 중에는 rebase로 main을 따라가고, 합칠 때는 merge(또는 PR의 squash merge)"입니다.
